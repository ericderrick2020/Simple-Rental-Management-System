ABSTRACT / EXECUTIVE SUMMARY
Many school libraries still record books, members and loans in notebooks and spreadsheets,
which leads to misplaced and duplicate records, slow searching and unclear loan tracking. This
project replaces those manual methods with the School Library Management System, a desktop
application built with Python, Tkinter and MySQL for use by a school librarian. The
application provides a secure login, a dashboard with live statistics, and modules for books,
nested categories, members, borrowing and returns, and reports. Beyond the approved
proposal, every physical copy of a book is stored as its own record with a unique copy number
and a status (Available, Borrowed, Damaged, Lost or Withdrawn), and books can carry a shelf
location and a cover picture. Business rules and validation are enforced in a separate data layer,
so duplicate ISBNs, duplicate emails, invalid loans and unsafe deletions are rejected with clear
messages. The design was developed through eight flowcharts and a relational schema of six
tables. Testing covered 38 planned cases: 28 were run and passed, none failed, and 10 input-
validation and error cases are still to be run. The result is a working, easy-to-use system that
meets all seven Phase 1 objectives. Limitations such as the fixed loan period, the absence of
fines and the lack of report export are recorded for future work.

CHAPTER 1 - INTRODUCTION AND PROJECT OVERVIEW
1.1 PROJECT BACKGROUND / INTRODUCTION
Libraries support teaching, learning and research by giving students and teachers access to
educational materials. Many schools, however, still manage their libraries with notebooks,
record books or spreadsheets. These methods work for small collections, but as books and users
increase, searching, updating records and tracking borrowed materials becomes slow and error-
prone.
The School Library Management System is a desktop application developed in Python. It lets a
librarian register books, keep track of every physical copy, manage students and staff as library
members, issue and return books, and view reports. Data is stored in a MySQL database, so it
remains available after the program is closed. The application is intended for school librarians,
and it benefits students and staff through faster, more accurate service.
This report connects the finished application to the proposal approved in Phase 1 and the design
completed in Phase 2.
1.2 PROBLEM STATEMENT
Many school libraries still use manual methods to manage books, members and borrowing
records. This often leads to misplaced records, duplicate entries, inaccurate information and
difficulty tracking borrowed books. It also makes searching for books and preparing reports
slow and inefficient. Therefore, a computerized School Library Management System is needed
to automate library operations, improve record accuracy and provide faster access to
information.
The problem addressed is unchanged from Phase 1.

2.2 SYSTEM ARCHITECTURE
Figure 1 system architecture
How the layers work together: the user clicks in a screen (ui/). The screen checks simple
things such as empty fields and numbers, then calls a function in models/. The model applies
the business rules (for example, an ISBN must be unique, or a borrowed copy cannot be
deleted), runs the SQL through db.py and returns a result or raises a ValueError with a readable
message. The screen shows that message in a dialog. Screens never talk to the database directly.

2.4 DATA STRUCTURE / DATABASE DESIGN
The final storage method is a MySQL database named school_library_db, running on XAMPP.
It has six tables. Data stays saved when the application is closed. Cover pictures are stored as
files in the covers/ folder, and only their relative path is saved in the database.
Relationships: one category has many books (and categories can contain sub-categories
through parent_id); one book has many copies; one copy has many loan records over time; one
member has many loan records.

2.5 USER INTERFACE / MENU DESIGN
The application is a graphical desktop program. The Login window is a single card with
username and password fields. After login, the Dashboard has a dark sidebar on the left with
Home, Books, Categories, Members, Borrow / Return, Reports and Log Out, and a content
area on the right that changes with the selected item.
Figure 10  system architecture
Home: greeting, five statistic cards, four quick-action buttons and the 15 most recent
borrowing records (overdue in red, returned in grey).
Books: search bar, book table, cover and details panel, and buttons Manage Copies, Edit
Selected, Delete Selected, plus Add Book.
Categories: tree of parent and child categories with buttons to add, rename and delete.
Members: search bar, member table, and Register, Edit and Deactivate actions.
Borrow / Return: Book, Copy Number and Member selectors (or a typed copy number), an
Issue Book button, and a table of current loans with Mark as Returned.
Reports: six statistic cards and four tabs: Available Books, Registered Members, All Copies
and Status, Borrowing History.

3.4 IMPLEMENTATION OF MAJOR FEATURES
3.4.1 Login
User action: types username and password and presses Log In.
Processing: both fields must be filled. verify_login hashes the password with SHA-256 and
compares it with the stored hash.
Data: reads the users table. On first run the default admin account and a starter category tree
are created.
Result: the dashboard opens, or "Incorrect username or password." is shown.
3.4.2 Books: add, edit, delete and search
User action: clicks Add Book and fills the form (title, author, category, year, ISBN, shelf,
number of copies, optional cover). Edit and Delete work on the selected row. The search bar
accepts any keyword.
Processing: required fields and numbers are checked in the form. add_book rejects a duplicate
ISBN, inserts the book, then creates the requested number of copies. update_book rejects an
ISBN used by another book and replaces the cover file if a new one is chosen. delete_book
refuses if any copy is on loan or if the book has borrowing history. search_books matches title,
author, ISBN, shelf, category path (so a parent category also finds its children's books) and
copy number.
Data: books and book_copies tables; cover files in covers/.
Result: the table refreshes. The side panel shows the cover and details of the selected book,
including copies available out of total.
3.4.3 Categories
User action: on the Categories screen adds a top-level category, adds a sub-category under the
selected one, renames or deletes.

=== PAGE 30 ===
29
Processing: names cannot be empty or repeated at the same level. A category with sub-
categories or books cannot be deleted.
Data: categories table, using parent_id for nesting. Books display the full path, for example
Science > Physics.
Result: the tree refreshes and shows how many books are directly in each category.
3.4.4 Copies and status
User action: selects a book and clicks Manage Copies. Can add copies, set the selected copy
to Available, Damaged, Lost or Withdrawn (with a note), or remove a copy.
Processing: copy numbers are generated as B + book id + -C + sequence, for example
B0001-C03. A borrowed copy cannot be changed or removed. A copy with borrowing history
cannot be deleted; it should be marked Withdrawn.
Data: book_copies table.
Result: the list shows each copy's number, status, borrower, due date and notes, colour-coded
by status.
3.4.5 Members
User action: registers or edits a student or staff member, and deactivates members who leave.
Processing: name and type are required; an email, if given, must contain "@" and be unique.
Deactivation is blocked while the member has borrowed books.
Data: members table. Deactivated members stay in the database so history is kept.
Result: the table refreshes. Inactive members no longer appear in the issue list.
3.4.6 Issuing a book
User action: on Borrow / Return chooses a book, then one of its available copy numbers, then
a member. Alternatively types or scans a copy number.
Processing: issue_book checks the copy is Available and the member is Active, creates a loan
with a due date 14 days away, and sets the copy to Borrowed.
Data: borrow_records and book_copies tables.
Result: a message shows the due date; the loan appears in the Currently Borrowed table.
3.4.7 Returning a book
User action: selects a loan, clicks Mark as Returned and answers whether the copy is in good
condition.
Processing: return_book sets the return date and marks the loan Returned. The copy becomes
Available (good) or Damaged (not good). Overdue loans are shown in red before return.
Data: borrow_records and book_copies tables.
Result: the loan leaves the current list and stays in the history.

3.4.8 Dashboard and reports
User action: opens Home or Reports.
Processing: get_library_statistics counts titles, copies (excluding Withdrawn), available

every copy with status, and the full borrowing history.
Result: live figures and tables. Reports are shown on screen and cannot be exported in this

rules and raise a ValueError with a readable message, which the screen shows in a dialog.

1 or more."

3.6 DATA STORAGE AND RETRIEVAL
All records are saved in MySQL the moment an action is confirmed (each change is
committed). When the program is closed and reopened, the screens read the same tables again,
so books, copies, members and loans are still there. Cover pictures are copied into the covers/
folder with a random file name, and the database keeps only that path. Deleting or replacing a
cover removes the old file. Loan history is never deleted: members are deactivated instead of
removed, and copies with history are marked Withdrawn instead of deleted.

CHAPTER 5 - USER GUIDE AND PROJECT COMPLETION
5.1 SYSTEM REQUIREMENTS
• Computer running Windows, macOS or Linux
• Python 3.9 or newer with Tkinter (included in the standard Windows installer)
• MySQL Server, for example the one in XAMPP, running on localhost port 3306
• Python packages: mysql-connector-python and Pillow (listed in requirements.txt)
• Required files: the complete SchoolLibrarySystem folder, including schema.sql and the
covers folder
5.2 INSTALLATION / SETUP INSTRUCTIONS
1. Copy the SchoolLibrarySystem folder to your computer.
2. Open the XAMPP Control Panel and click Start next to MySQL.
3. Open http://localhost/phpmyadmin, choose the SQL tab, paste the contents of schema.sql
and click Go. (If you used the older version 1, run DROP DATABASE
school_library_db; first.)
4. If your MySQL password is not blank, edit config.py with the correct user and password.
5. Open a terminal in the project folder and run: pip install -r requirements.txt
6. Start the program with: python main.py
5.3 HOW TO USE THE APPLICATION
1. Step 1: Run python main.py and log in with admin / admin123 (created automatically on
first run).
2. Step 2: Use the sidebar to move between Home, Books, Categories, Members, Borrow /
Return and Reports.
3. Step 3: To lend a book: open Books and add the title with its copies (and optional cover),
open Members and register the borrower, then open Borrow / Return, choose the book,
copy number and member, and press Issue Book.
4. Step 4: To receive a book, select the loan and press Mark as Returned. Use Reports to
view statistics and history. Press Log Out when finished, then close the window.
5.4 KNOWN LIMITATIONS
• The loan period is fixed at 14 days and cannot be changed in the interface.
• There are no fines or reminders for overdue books; overdue loans are only highlighted.
• Reports are shown on screen only and cannot be exported or printed.
• There is one type of user. Passwords are hashed with SHA-256 without a salt, there is no
change-password screen and no screen for creating more librarian accounts.

=== PAGE 40 ===
39
• The program runs on one computer with a local MySQL database. There is no network,
web or mobile access.
• A book with borrowing history cannot be deleted; its copies must be marked Withdrawn.
• Data from the first version cannot be migrated automatically to the new tables.
• There is no backup or restore feature and no barcode scanning (copy numbers are typed
or selected).
• The interface has not been tested with very large collections.
5.5 RECOMMENDATIONS FOR FUTURE IMPROVEMENT
• Overdue fines and reminders for members.
• Export of reports to PDF or CSV and printing of copy labels with barcodes.
• Adjustable loan periods and borrowing limits per member type.
• Multiple librarian accounts with roles, salted password hashing and a change-password
screen.
• Book reservations and a student-facing search page.
• Backup and restore of the database.
• Automatic data migration between schema versions.

CHAPTER 6 - CONCLUSION
6.1 PROJECT SUMMARY
The project addressed the problem of manual, error-prone school library records. A desktop
School Library Management System was developed in Python with a Tkinter interface and a
MySQL database. It provides a secure login, a home dashboard, book management with nested
categories, shelf locations and cover pictures, copy-level tracking with statuses, member
management, borrowing and returns with due dates and overdue highlighting, and on-screen
reports. Validation and business rules in a separate data layer protect the records from
duplicates and unsafe changes.
6.2 ACHIEVEMENT OF OBJECTIVES
All seven Phase 1 objectives were achieved (Table 1.1 and Table 4.4). All 22 functional
requirements were implemented (Table 2.1). Of 38 planned tests, 28 were run and passed, none
failed, and 10 form-level and error tests are pending. The system also goes beyond the proposal
through copy-level tracking, nested categories and cover pictures.
6.3 LESSONS LEARNT
Technical lessons: separating the interface, business rules and database access made the
program easier to change, and it allowed the same rules to be tested without opening any
window. Designing the data around real objects matters: storing one row per physical copy
solved problems that a simple count could not. Putting constraints and checks in the data layer,
for example unique ISBNs and blocked deletions, prevents bad data whichever screen is used.
Testing against a real database found issues that reading the code did not.
Personal lessons: planning in phases made a large task manageable, and writing flowcharts
and a test plan before coding reduced rework. Requirements can grow during development, so
the design must be kept up to date and changes must be documented honestly. I also learnt to
record only the tests I have actually run.
6.4 REMARKS
The School Library Management System is a working, practical tool that lets a school librarian
keep accurate records of books, copies, members and loans and find information quickly. With
the limitations in Section 5.4 addressed in future versions, it can serve as a dependable library
system for a school.
